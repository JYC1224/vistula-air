# 遊戲式學習：設計與製作

使用者要求設計、製作、原型化或修改教學遊戲／遊戲式學習時套用本 Skill。若使用者只要純娛樂遊戲，依一般遊戲開發流程處理。若需求其實是在既有非遊戲活動上加點數、徽章或排行榜，先辨明那是遊戲化設計，並確認獎勵是否支持目標行為。

本 Skill 的設計原則整理自使用者提供的 Google 文件《數位遊戲式學習：概念、設計與教學應用》。文件中的供水決策與校園消息查證案例只作為設計例子，不當作真實領域資料或固定題材。

## 工作方式

1. **先讀專案脈絡。** 遵循專案的 `AGENTS.md`、現有架構、遊戲引擎、技術棧與美術慣例。判斷使用者要的是構想、設計規格、可玩原型，還是要直接修改現有遊戲；要求實作時就交付可玩的功能，不要只停在提案。不要替換現有工具或擴大功能範圍，除非需求需要。
2. **定義學習者與學習結果。** 記錄目標玩家、先備知識、使用情境及重要限制。把寬泛的「理解某主題」改寫為可觀察行動，例如「在給定三回合資料時，比較兩種方案並用數據說明成本差異」。一次聚焦少數核心目標；分清學習目標、遊戲勝利條件與參與度目標。
3. **讓玩法承載學習行動。** 依目標選擇適合的活動形式，例如回想練習、解謎、探索式模擬、資源管理、分支情境、角色扮演或合作查證。使用下列對齊關係檢查設計：

   `學習目標 → 玩家必須做的事 → 遊戲機制與狀態變化 → 可理解的回饋 → 能看出學習的證據`

   玩家若能不運用目標知識也輕易獲勝，調整規則、選項或計分，讓目標能力成為推進任務的有效方法。只有答題後發獎勵可適合記憶練習，但不等於概念已融入玩法。
4. **說清核心循環與規則。** 定義遊戲狀態、玩家可做的行動、規則如何改變狀態，以及一輪如何結束。建立短而清楚的核心循環（例如查看線索、形成預測、作選擇、觀察結果、解釋或修正），並確保每個重要選擇都有可理解的取捨或後果。模型中的假設、單位、時間順序與邊界條件要明確；沒有資料支持的領域規則標成假設或向使用者確認。
5. **用回饋和挑戰支持學習。** 把難度逐步增加；必要時先提供示範、提示或部分完成的支架，再依玩家掌握情況淡出。讓失敗指出可用線索，保留回看、重試或比較結果的機會。區分三種功能：回饋解釋行動或結果，獎勵標記進展或鼓勵參與，評量蒐集目標能力的證據。檢查玩家是否會為高分採取違背學習目標的捷徑。
6. **配合玩家與媒介。** 依先備知識、操作熟悉度、裝置和場域調整資訊量、節奏與支援。讓文字、圖示、顏色、音效及控制方式可理解且可調整；合作玩法中也要讓各玩家有實際資訊與決策責任。數位功能（狀態紀錄、自動計算、視覺化、分支、重播）只在能提供目標需要的經驗時加入；簡單介面也能支援完整的學習遊戲。
7. **範圍合宜地製作。** 先找出核心決策或學習關係，做足以呈現它的最小可玩切片；使用既有專案技術與素材慣例。若使用者要的是完整遊戲，仍需完成其要求的主要流程，而非把原型當成最終交付。提出原型或評估建議時，讓每次試玩回答具體問題（例如玩家是否讀懂線索、是否根據回饋修正）。除非使用者要求驗證或測試，依專案一般工作需要完成實作，但不要自行新增或執行測試。
8. **把學習成效說得準確。** 分開描述參與、當下學習、延後保留與新情境遷移。分數、通關、停留時間與重玩次數只能說明可見行為，不能單獨證明理解。證據應對應目標，例如決策理由、正確操作、對新情境的解釋；若使用者要求成效評估，說明比較條件與推論限制，並把觀察結果用來調整玩法。

## 交付格式

- **只要構想或設計規格：** 依 [設計簡報與範例](references/design-brief.md) 整理適用的欄位；簡單需求可精簡，不要為了填表而增加無關細節。
- **要實作遊戲：** 依專案現況完成可玩的結果，簡要交代學習目標如何落在玩法、哪些主要流程已完成，以及仍依賴哪些假設。避免只給通用建議或空泛的教育效益宣稱。
- **資訊不足時：** 對可合理推定的美術、題材或小型玩法細節採取清楚標記的假設並繼續；只有在受眾、學習目標、平台或內容正確性會改變整體方案時，才提出精簡的必要問題。
